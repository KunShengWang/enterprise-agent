# 生产发布规范

生产发布规范适用于所有会影响线上用户、核心业务、数据结构、权限策略、支付链路、订单链路和运营配置的变更。Agent 回答发布相关问题时，必须优先依据发布单、审批状态、灰度计划、回滚预案和监控结果，不能建议绕过审批直接上线。

发布前必须创建发布单。发布单需要包含变更背景、影响范围、涉及服务、数据库变更、配置变更、依赖系统、发布窗口、负责人、验证人和回滚负责人。高风险生产发布必须完成发布单审批、回滚预案、灰度验证和发布后监控。未经审批不得直接上线。

发布前检查包括代码合并状态、自动化测试结果、配置中心变更、数据库脚本、接口兼容性、消息兼容性和权限变更。涉及数据库字段新增、索引创建、数据迁移或批量更新时，需要明确执行顺序和回滚方案。涉及外部支付、短信、物流或第三方系统时，需要确认对方接口状态和限流策略。

灰度发布是降低风险的重要手段。灰度范围可以按用户比例、城市、租户、门店、业务线或内部账号控制。第一阶段通常只开放给内部账号或低风险用户，确认核心指标稳定后再逐步扩大比例。灰度期间需要重点观察错误率、接口延迟、订单创建成功率、支付成功率、消息积压和用户投诉。

发布过程中必须有人值守。发布负责人负责推进流程，研发负责人负责技术问题处理，测试负责人负责线上验证，运维负责人负责监控和回滚支持，业务负责人确认业务指标。发布窗口内不得同时进行多个互相影响的高风险变更，避免故障时无法判断根因。

回滚预案必须在发布前准备好，而不是发布失败后临时编写。回滚预案应说明回滚触发条件、回滚命令、配置恢复方式、数据库兼容策略、数据修复步骤和验证方式。发布失败时应优先执行回滚预案，并记录失败原因。如果数据库变更不可逆，需要提前设计兼容方案，例如先加字段再双写，验证稳定后再切读路径。

发布完成后需要观察核心指标和错误日志，确认没有明显业务异常。观察时间根据风险等级决定，普通发布至少观察 15 分钟，高风险发布至少观察 30 分钟。核心指标包括接口成功率、平均响应时间、错误日志数量、数据库慢查询、队列积压、支付回调、订单状态流转和业务转化率。

如果发布后出现异常，应立即判断是否达到回滚条件。典型回滚条件包括核心接口错误率持续升高、订单无法创建、支付失败率异常、用户投诉集中出现、数据库连接池耗尽、消息积压快速增长或关键业务指标明显下降。达到回滚条件时，不应继续观察等待，而应按预案执行回滚。

发布记录必须完整保留。需要记录发布开始时间、结束时间、发布版本、执行人、审批人、灰度范围、验证结果、异常情况、回滚动作和最终结论。发布后的问题如果进入故障流程，需要关联故障工单和复盘报告。没有记录的发布不符合审计要求。

Agent 可以帮助查询发布流程、提醒发布检查项、生成发布单草稿和解释回滚规则。但涉及是否允许上线、是否跳过灰度、是否忽略审批、是否直接修改生产数据时，必须提示需要负责人确认或人工审批。对于高风险发布请求，Agent 应优先给出风险提示和标准流程，而不是直接给出执行命令。
